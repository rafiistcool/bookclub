# MED (#43) implementation notes

Owner: MED. These notes record what the media package built, where it deviates from the design documents, the Python tests that are reasoned rather than ported, and what FE, PAR and the integrator need to know. The design documents themselves are unchanged.

## How it works

- **Stored pictures.** Every picture is a `media` row plus its variants in the `MediaStore` under `object_key(kind, public_id, variant)`; `storage_key` is `storage_prefix(kind, public_id)`. Uploads and fetched covers are WebP (`l` and `s` for covers, `a` for avatars). `width`/`height` are the largest variant's, `byte_size` is the sum of the stored variants, `sha256` is the hash of the bytes as received (upload or Open Library response).
- **The picture pipeline** runs on the blocking pool, at most two pictures at a time (`MediaService::process`, a semaphore: a 25 Mpx picture can take a few hundred MB while it is decoded and resized). Nothing CPU-bound runs on the async runtime: the upload's SHA-256 is computed once, inside `process`; the backfill samples stored pictures through `MediaService::dominant_color` (same semaphore, blocking pool); the takedown hashes variants with `service::sha256_all` (blocking pool).
- **Open Library covers.** A cover row from `ingest::ol_cover_media` gets its bytes on first need: `GET /media/…`, the spine backfill or the prefetch worker call `MediaService::ensure_cover`. It fetches `{OPENLIBRARY_COVERS_URL}/b/id/{cover id}-L.jpg?default=false` through `outbound::get_bytes` with `RetryPolicy::MEDIA` (the `ol_covers` throttle, 10 s wait, checked redirects, 1.5 MB cap), converts it, stores `l` and `s`, samples the spine colour and fills the row (`… WHERE removed_at IS NULL AND storage_key IS NULL`). Concurrent calls for one media id share one fetch (a `Shared` future over a spawned task, so a caller that goes away does not cancel it for the others; the task removes its own entry when it ends).
- **Outcomes of a fetch** (spec/shelf.md §6 risk 15): a refused redirect, a body over 1.5 MB, a 404 or 410, or bytes that are no usable picture settle as "no cover": `fetch_failed_at = now()` (no new request for 7 days) and `dominant_color = ''`. Throttling is `Busy`; a transport error, a timeout, a 5xx after the one retry or any other status is `Failed`, which records nothing.
- **Takedowns win every race.** `removed_at` is read first everywhere (serve, fetch, backfill), and the fetch only fills a row that is not removed. A fetch that stored bytes after a takedown sees its `UPDATE` match nothing and deletes the bytes again (tested: the waiting request answers 410 and the store is empty).
- **Prefetch.** `prefetch(ids)` puts ids on a bounded channel (500); when it is full the rest of the batch is dropped. `run_prefetch` drains it one cover at a time with `PREFETCH_POLICY` (`MEDIA` with a 30 s throttle wait), pausing for the cooldown when Open Library is busy. A browser request for a cover the worker is fetching joins that fetch and so runs under the worker's policy. That does not stretch the 10 s of conventions §8 in practice: only MED books `ol_covers` slots, every request path refuses a slot more than 10 s ahead and the worker books one at a time, so the worker's slot is never more than 10 s plus one interval (0.2 s) away. The 30 s only lets the worker squeeze in behind a full 10 s of browser requests instead of dropping the id. It takes the channel's receiver when it starts and hands it back when it stops, so it can be started again (tests do).
- **Avatars.** `PUT` stores the new picture first, then one transaction locks the user row, deletes every avatar row of the user that was not taken down (the current one and any a crash left behind), registers the new row and points `users.avatar_media_id` at it; the old bytes are deleted after the commit, the new ones if the transaction fails. `DELETE` does the same without a new row. Both answer `auth::user_out`.
- **Uploads and removed pictures.** Both upload routes run the pipeline first, then refuse (400 `This picture was removed`) an upload whose SHA-256 (of the bytes as received, from `Processed::sha256`) matches a removed `media` row or a row of `media_removed_hashes`, and only then store anything. A refused upload leaves no row and no bytes.
- **Cover uploads.** The photo is processed and stored, then one transaction locks the work `FOR UPDATE` (following merges: CAT's rule for writes that store a `work_id`, so a merge either sees the cover or the upload lands on the surviving work), checks the edition again, registers the media row and calls `ingest::set_cover(target, media, Source::User, only_if_empty = true)`; the target is the edition with `edition_id`, else the work. When that sets nothing, the upload becomes a `cover_replace` request (`work_id` = the current work, `edition_id`, `media_id`, `payload {}`, `created_by`), which CAT's approve applies with provenance `admin`. 200 `{book: BookOut}` (in the edition's context) or 202 `{request_id}`.
- **Takedown** (`take_down_locked(conn, store, media_id, admin_id)`, used by resolve `remove` and `DELETE /api/admin/media/{public_id}`): locks the media row `FOR UPDATE`, reads every stored variant and records its SHA-256, and the row's own `sha256`, in `media_removed_hashes`, sets `removed_at` and clears `storage_key`, calls `ingest::clear_media`, then resolves every open report of the picture as `removed`. A store error fails the takedown (500, nothing changed), so a picture is never removed without its hashes; a variant whose bytes are missing is skipped with a warning. Lock order media row → works/editions → reports, the order ingest, `set_cover`, CAT's cover approval and `merge_works` use (a test shows a takedown waiting for an ingest that attaches the cover, then clearing it). The bytes under `storage_prefix(kind, public_id)` (and the old `storage_key`) are deleted after the commit. The row and its hash stay.
- **Spine backfill.** The pending books are the caller's shelf entries whose shown cover (the entry's edition's, else the work's; not removed) has `dominant_color IS NULL`, by work id; 12 per call, resolved concurrently, each picture once. A stored picture without a colour is sampled from its largest variant without a request; an Open Library cover without bytes goes through `ensure_cover`. `remaining` is 0 after any unresolved (`Busy`/`Failed`) picture. No pool connection is held while Open Library is asked.

## Deviations and decisions

1. **`/media` error answers.** 404 `Not found` for an unknown or malformed public id, a variant the picture's kind does not have, a stored row whose bytes are missing, and an Open Library cover that settled as "no cover"; 410 `This picture was removed`; 429 `The library is busy. Wait a few seconds and try again.` (the catalog's busy string, with `Retry-After` while a cooldown runs) when the `ol_covers` throttle refuses; **502 `Could not load the cover right now. Try again.`** when Open Library did not answer (endpoint-map says 404 for "a failed OL fetch"; conventions §8 lists 502 among the `/media` answers, so transient failures are 502 and only a settled "no cover" is 404). Every non-200 answer carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
2. **Upload body errors keep the legacy strings.** A body that is not multipart (a JSON body too) or a form without a `file` part (or with `file` as a plain text field) is 400 `Use a JPEG, PNG, WebP, or GIF`, a `file` part over 50 MiB is 400 `That picture is too large (50 MB max)` (spec/auth.md §1.6). `ApiMultipart`'s own rejection (`Field required`) and `ApiMultipart::file` (one string for both cases) cannot express that, so the handlers take `Result<ApiMultipart, AppError>` and read the parts themselves (`upload::read_picture`). A body that passes the route's body limit while it is read is 400 `That picture is too large (50 MB max)`; another malformed body is 400 `Use a JPEG, PNG, WebP, or GIF`. Text fields are capped at 1 KiB.
3. **The `Content-Length` check comes before the multipart check**, as in Python: a non-multipart request with an oversize `Content-Length` is 413.
4. **A taken-down picture's bytes are refused as an avatar too**, not only as a cover (`media_removed_sha256_idx` and `media_removed_hashes` cover both). Replacing or deleting an avatar never deletes a taken-down row, so its hash keeps the file out; account deletion does delete it, and then `media_removed_hashes` keeps it out (deviation 16).
5. **Avatar uploads have no rate limit** (parity, spec/auth.md: "avatar upload has no rate limit"); the replaced picture is deleted, so storage stays bounded, and the pipeline's two-at-a-time semaphore bounds the CPU. Cover uploads use `upload_user` (30 per day per user), counted after the body, work and edition checks and before the pipeline and the removed-hash check.
6. **A taken-down avatar stays referenced by `users.avatar_media_id`**; `auth::user_out` (and every loader) ignores removed media, so `avatar_url` is null. The takedown therefore never locks a user row (no lock-order conflict with avatar writes or account deletion). The next upload points the user at the new row.
7. **Open requests of a taken-down picture stay open.** CAT's approve answers 400 `This picture was removed` for them and its `EditRequestOut` shows the cover fields as null; MED does not write `catalog_edit_requests` beyond filing `cover_replace` requests.
8. **The cover fetch asks for `-L.jpg`**, not the legacy `-M.jpg`: one fetch gives both stored sizes. `?default=false` makes Open Library answer 404 instead of its 1×1 placeholder.
9. **Spine colours belong to pictures** (`media.dominant_color`), not to books. A new cover is a new, unsampled picture, so the legacy "reset on cover change" is automatic. A book without a cover has no picture and is simply never pending (Python stored `''` on the book). A fetch that settles as "no cover" writes `''` on the picture, so the backfill does not ask again; a successful fetch a week later overwrites it.
10. **Colours are sampled from the stored `l` variant** for uploads and fetches (the 4,000,000-pixel limit of the legacy byte contract applies to `dominant_color(bytes)`, which the backfill uses for stored pictures). The thumbnail follows Pillow (`thumbnail((48, 48))`: its size rounding, an integer box reduction with reducing gap 2, then bicubic). The median cut splits the most populous box along the widest luma-weighted channel (77/150/29) at the pixel median, like Pillow's `splitlists`, and each pixel counts for its nearest palette colour. On 12 random covers made with Pillow (`tests/fixtures/images/pillow/`), 10 give the identical colour and 2 differ by one split decision of a near-tie (the spec asks for the qualitative properties only).
11. **Reports.** Only covers can be reported (`reports.target_kind` allows `cover`): an avatar's public id is 404 `Not found`, like an unknown one. A taken-down picture can still be reported (201); the queue shows it as removed. `reason` outside the four values is 400 with the pydantic enum message `Input should be 'copyright', 'wrong_book', 'offensive' or 'other'`; `details` is trimmed and silently cut at 2000 characters (like CAT's request notes); `null` is `""`. The report records the book that shows the picture (the first edition and its work, else the first work, else the book a `cover_replace` request proposed it for). 20 reports per user and day (`report_user`), counted after the 404.
12. **Resolving.** `action` outside `remove`/`dismiss` is 400 `Input should be 'remove' or 'dismiss'`; an unknown report is 404 `Not found`; a resolved one is 409 `This report was already resolved` (also when another admin resolves it concurrently: the whole transaction, a takedown included, is rolled back). `remove` resolves every open report of the picture; `DELETE /api/admin/media/{public_id}` does the same and is idempotent (204 again for a removed picture).
13. **`ReportOut`** is `{id, reason, details, status, media_public_id, removed, cover_url, cover_thumb_url, book: BookOut|null, created_by: UserSummary|null, created_at, resolved_by: UserSummary|null, resolved_at}`; the cover URLs are null once the picture was taken down.
14. **`edition_id` on a cover upload** is a multipart text field: empty means none; a non-number is 400 `Input should be a valid integer, unable to parse string as an integer`; an edition of another book is 400 `That edition belongs to another book` (checked again under the work lock).
15. **"No outbound request" after a takedown** (#43 acceptance) is read as "no request for the picture": a refresh and a first-view enrichment are themselves requests for the work's metadata (`/works/…json`, `/search.json`) and still run; what they must not do is fetch, attach or store the removed cover, and no `/b/id/…` request is made after the takedown.
16. **"A re-upload of the same file" includes the files readers have** (#43 acceptance). `media.sha256` is the hash of the bytes as received (the uploader's file, Open Library's JPEG); every other reader only ever got the re-encoded WebP variants from `/media/…`, whose hashes the schema did not keep. Migration `1300_media_removed_hashes.sql` adds `media_removed_hashes (sha256 bytea PRIMARY KEY, media_id → media ON DELETE SET NULL, variant, created_at)`: the takedown records the hash of every stored variant (`l`, `s`, `a`, `variant` = its name) and of the original (`variant` NULL), and uploads check it next to `media::shared::is_removed_hash`. The copy of the original's hash outlives the media row: account deletion deletes the user's avatar rows, taken-down ones included (AUTH's `auth/deletion.rs`), and the hashes keep both files out of a new account. Still not refused: a file re-encoded again (a screenshot, another format), since matching is by exact SHA-256 as before; and any file for an Open Library cover taken down before its bytes were ever fetched (`sha256` NULL, no variants): we never had or served its bytes, and fetching them to hash would download the removed picture again.

## Strings

New detail strings (not in endpoint-map §11):

- `Could not load the cover right now. Try again.` (502 on `/media`). An `<img>` never shows it; FE need not map it.
- `The library is busy. Wait a few seconds and try again.` (429 on `/media`): CAT's string, byte for byte.
- `This report was already resolved` (409, admin only).
- `Input should be 'copyright', 'wrong_book', 'offensive' or 'other'` and `Input should be 'remove' or 'dismiss'` (400, only for a client that sends other values).

Strings of endpoint-map §11 that MED returns: the four picture strings (`error::msg::PICTURE_*`, already mapped), `This picture was removed` (§11.3, 400 on an upload and the 410 detail), `Slow down a little. Try again later.`, `No such book.`, `That edition belongs to another book`, `Not found`, `Not signed in`.

## For FE

- `avatar_url` and every `cover_url`/`cover_thumb_url` are same-origin `/media/{public_id}/{variant}` URLs; treat them as opaque. They are immutable: a new picture has a new URL.
- `PUT /api/auth/me/avatar` (multipart `file`) answers `UserOut`; the picture is a 256×256 WebP. `DELETE` answers `UserOut` too.
- `POST /api/books/works/{work_id}/cover` (multipart `file`, optional `edition_id`): 200 `{book}` when the photo is the cover now, **202 `{request_id}`** when it waits for an admin ("Thanks, an admin will look at it"). 429 after 30 uploads a day.
- "Report cover" posts `{reason, details?}` to `/api/media/{cover_public_id}/reports`: 201 `{id}`, 429 after 20 a day.
- `POST /api/shelf/spine-colors` keeps the legacy contract; its keys are work ids (`BookOut.id`).
- The admin queue (`#54`): `GET /api/admin/reports`, `POST /api/admin/reports/{report_id}/resolve` `{action}`, `DELETE /api/admin/media/{public_id}`.
