## `update.sh` (Q8 = A)

Every run, from `bookclub-update.timer` or by hand, in `COMPOSE_DIR`:

1. **Guards.** `UPDATE_WAIT_SECONDS` must be a positive integer (else `die`, before any pull or ping). One run at a time (`flock -n` on `BACKUP_DIR/.update.lock`; a second run logs `another update.sh is running` and exits 0). The app container is the app service's container without the one-off containers of `docker compose run` (`app_container`). With no app container (the stack is down, as in a restore) or an app that is not `running` or `restarting` (stopped by hand, as for the legacy import), it logs why and exits 0, without pulling, starting anything or pinging. **It never starts an app that is not running.**
2. **`docker compose pull --quiet app`.** The image is the app's line of `docker compose config --images app` that contains `/bookclub-server:`, as in `smoke-test.sh` (compose prints the dependencies' images too). While the tag has not moved, the pull is a manifest request and downloads nothing. Compose prints progress even with `--quiet`, so the output goes to the journal only on a failure. A failed pull logs `error: cannot pull <image>; nothing was changed` and exits 1 **without a ping**: a short registry outage (a Forgejo restart) alerts only when it outlasts the heartbeat check's grace time.
3. **The decision:** the ID of the image the tag names after the pull (`docker image inspect -f '{{.Id}}'`) against the image the app container runs (`docker inspect -f '{{.Image}}'`). Comparing with what runs, not with a remembered digest, means that a new pin in `.env` is an update like a release, and that a failed update is not forgotten.
4. **Nothing to do** (same image; `BACKUP_DIR/update.failed` is removed): `running healthy` pings `<url>/0` and logs `<image> is up to date (<repo>@sha256:…), and the app is healthy`; `running starting` exits 0 without a ping (the next run decides); anything else (`running unhealthy`, `restarting …`) logs `error: the app runs <image> (…), but is <status>`, pings `<url>/1` with that line, and exits 1. A failed update therefore keeps the check down until it is fixed, and a crash-looping app is caught although Docker resets its health to `starting` on each restart.
5. **The wait after a failed update.** When `BACKUP_DIR/update.failed` names this image and is less than `RETRY_AFTER` (3600 s) old: `error: the update to <image> (…) failed at <time>; the next try comes after <time>, or at once after rm <file>`, ping `<url>/1` with that line, exit 1. No backup, no `compose up`.
6. **The update**, logged to the journal and to `BACKUP_DIR/update.log` (mode 0600):
   1. `<url>/start`;
   2. `backup.sh` (its own lock, heartbeat and log). A failure stops the update with `the backup failed, so the app was not updated`; the app keeps running the old image, and the image waits an hour (`update.failed`);
   3. the app's state again (`app_container`, `container_status`): when it is no longer `running` or `restarting`, or its container is gone, `the app is <state> now, so it was not updated: it was stopped while the backup ran, and a stopped app stays stopped`, exit 1 (so `<url>/1`), no `compose up` and no `update.failed`: once the app runs again, the next run updates at once;
   4. `docker compose up -d --no-deps --wait --wait-timeout $UPDATE_WAIT_SECONDS app`: only the app is recreated (`--no-deps`, so postgres is never recreated by the timer). On failure: `the app did not turn healthy on <image> (docker compose logs app); the backup from before the update is the latest snapshot`;
   5. a check that the container runs the new image and is `running healthy`; failures of 4 and 5 also write `update.failed`, and success removes it;
   6. the image the app ran before is removed when no tag names it any more (`docker image inspect -f '{{join .RepoTags " "}}'` is empty); a pinned or older tag that still names it keeps it;
   7. `<url>/<exit status>` with the last 50 lines of the log.

**Exit status:** 0 when nothing was to do, the app is starting, the run was skipped, or the update succeeded; 1 on a failed update, an app stopped during the backup, a failed image that waits for its next try, an unhealthy app, an unreachable registry or a bad `UPDATE_WAIT_SECONDS`; 2 on a usage error.

### Decisions

- **Settings in `backup.env`, not a new `update.env`.** `update.sh` runs `backup.sh`, which reads `backup.env`; both must name the same `COMPOSE_DIR`, and a second file would let the two drift apart. `update.sh` reuses `load_config`, so it also refuses to run without a working backup setup (`RESTIC_REPOSITORY`, a readable `RESTIC_PASSWORD_FILE`), which every update needs anyway. New settings: `UPDATE_HEARTBEAT_URL` (empty: no ping) and `UPDATE_WAIT_SECONDS` (default 300; a positive integer, else `update.sh` fails). `load_config` only sets the default: a bad value there would stop `backup.sh` and `restore-test.sh` before their first ping.
- **The ping policy:** `/0` after every healthy check (every 3 minutes), `/start` and `/<status>` around an update, `/1` for an unhealthy app, while a failed image waits for its next try, and for an app stopped during the backup, nothing for a registry error or a skipped run. The README recommends a healthchecks.io check "update" with a period of 5 minutes and a grace time of 1 hour: an update can wait for the backup lock (the nightly backup, the Sunday check and restore test) after its `/start`.
- **No automatic rollback.** A failed update leaves the app on the new image, unhealthy; rolling back automatically would start an older version on a database the newer one may have migrated. The operator pins `BOOKCLUB_TAG` (or restores), and the heartbeat stays down until then.
- **Rollback by pinning keeps working with the timer:** a pin is a tag change like a release; the next run backs up and starts that version, and later releases leave it alone. Tested below.
- **The timer:** `OnCalendar=*:0/3`, `AccuracySec=15s`, not `Persistent` (a missed check needs no catching up). A run that is still busy when the timer elapses is not started twice (oneshot). A failed run leaves the unit `failed`, and the next elapse starts it again (tested).
- **The service:** `Type=oneshot`, `Requires=`/`After=docker.service`, `network-online.target`, `TimeoutStartSec=4h` (up to 3 h waiting for the backup lock), `PrivateTmp`, `ProtectSystem=full`, `NoNewPrivileges`, like the backup units, and `Environment=DOCKER_CONFIG=/root/.docker`: a system service without `User=` gets no `HOME` from systemd, and the pull needs root's `docker login`. Not niced: an update should finish quickly; its backup is short.

### A fix in `backup.sh` (found while building `update.sh`)

`docker compose ps -a -q app` also lists the one-off containers of `docker compose run app …` (checked with Compose v5.6.1: the label `com.docker.compose.oneoff=True`). `backup.sh`'s `check_media_mount` passed both IDs, joined by a newline, to `docker inspect`, so **a backup failed while any `docker compose run app` container existed**: on `phase-2`, `backup.sh` exited 1 with `Error: no such object: <id>\n<id>` while a one-off `sleep` container ran next to the app. The importer, `rematch-legacy` and the README's `df -h /tmp` check are all such containers. `app_container` in `backup-lib.sh` now skips one-off containers, and both scripts use it. With the fix, the same backup exited 0.

"Reverse proxy" step 2 points there.
- Sources: Docker, "Packet filtering and firewalls" (https://docs.docker.com/engine/network/packet-filtering-firewalls/): published-port packets "are diverted before it reaches the `INPUT` and `OUTPUT` chains that ufw uses"; Docker, "Docker with iptables" (https://docs.docker.com/engine/network/firewall-iptables/): `DOCKER-USER` is "a placeholder for user-defined rules that will be processed before rules in the `DOCKER-FORWARD` and `DOCKER` chains", and restricting sources means "a negated rule at the top of the `DOCKER-USER` filter chain".

## Backups, option A: Storage Box snapshots

The Wave 1 security review's finding 3 (`docs/phase1/security-review.md`, "Phase 2 Wave 1", "The VM can delete its own off-site backups") offered three fixes; Rafael chose A. It needs no code: README "Backups" gained "Storage Box snapshots" (set-up in the console, how far back, space, credentials) and "Restore" gained "Restoring from a Storage Box snapshot" (read-only restore with `--no-lock`, then a rollback or a new repository). "Setting up" step 1 now also turns on SSH support (port 23) and "External Reachability".

Hetzner's documentation, read on 2026-10-29:

- "Storage Box Snapshots", https://docs.hetzner.com/storage/storage-box/snapshots/ (last change 2026-09-02): automatic snapshots on a schedule, manual ones kept until deleted; slots per plan BX11 10, BX21 20, BX31 30, BX41 40, and once the automatic slots are full the oldest is deleted as a new one is taken; snapshots are free but use the box's capacity, a new one takes no space and grows by later changes and deletions; they live in `/.zfs/snapshot`, or `/home/.zfs/snapshot` over SSH on port 23, one subfolder per snapshot that mirrors the box; "It is not possible to write to the `/.zfs` directory or its subfolder"; "Display snapshot directory" in the console shows or hides it; a restore undoes all changes since the snapshot, newer data and newer snapshots included; snapshots are "not full backups" and restore only the same box.
- "Creating Storage Box snapshots", https://docs.hetzner.com/storage/storage-box/getting-started/creating-snapshots/ (last change 2026-09-18): console path "Storage Boxes" → the box → "Snapshots" → "Enable automatic snapshots", choose when and the maximum number of slots, "Save".
- "Access with SSH/rsync/BorgBackup", https://docs.hetzner.com/storage/storage-box/access/access-ssh-rsync-borg/ (last change 2026-09-18): port 23, the restricted shell's commands (including `ls`), only `/home/` writable, relative paths recommended.
- "Storage Box Access Overview", https://docs.hetzner.com/storage/storage-box/access/access-overview/ (last change 2026-09-18): "External Reachability" must be enabled in the console ("Change settings") to connect from outside Hetzner's network; port 23 (SFTP, rsync, Borg) is activated in the console.
- Hetzner API changelog, https://docs.hetzner.cloud/changelog: Storage Boxes moved to the API at `api.hetzner.com` on 2025-06-25 (the Robot Storage Box endpoints were removed on 2025-07-30); on 2025-10-21, "Enable Snapshot Plan" made `hour` and `minute` required, and "Rollback Snapshot" takes `snapshot` (name or ID). So an API token can roll back or delete: the README forbids Console logins and API tokens on the VM.

What the README derives from that: the VM's SFTP key cannot delete or alter a snapshot; daily snapshots after the 03:30 backup (06:00 suggested; the console's time zone is to be checked, I found no statement of it); all of the plan's slots (BX11: 10 days back); the extra space is about 10 days of database dumps plus the pictures deleted in that time, because `forget --prune` deletes what the snapshots then keep; restoring reads the repository at `sftp:bookclub-backup:.zfs/snapshot/<snapshot>/bookclub` (relative to the home directory, which is `/home` on port 23) with `--no-lock`, through a copy of `backup.env` in `BACKUP_ENV`.

## Review round 1

Reviewers examined DEP2; every finding was real, and all are fixed:

- **An app stopped during an update's backup was started anyway** (two reviewers, major). `update()` now reads the app's state again after `backup.sh` and stops before `compose up` when the app is no longer running (see `update.sh`, step 6.3). It exits 1 and pings `/1`, so the `/start` gets an end, and writes no `update.failed`, so the update follows as soon as the app runs again. Stopping `bookclub-update.timer` does not stop a run in progress, so the README now waits for one after stopping the timer: `flock /var/lib/bookclub-backup/.update.lock true` (update.sh's own lock). The reviewers' other suggestion, `while systemctl is-active -q bookclub-update.service; do sleep 10; done`, would not wait: on this VM (systemd 257), a running `Type=oneshot` unit is `ActiveState=activating`, and `systemctl is-active` printed `activating` and exited 3 (a transient `systemd-run --user -p Type=oneshot sleep 8`). Used in "Updates and rollback", "Rollback", "The legacy import" step 2 and "Restoring for real"; the cutover text for the integrator is below.
- **Snapshot restore ran `backup.sh` against the broken repository** (two reviewers, minor) and **kept the attacker's access** (major). "Restoring from a Storage Box snapshot" is rewritten: (1) take the box back: reset the box password in the console, new key on the new VM, replace `.ssh/authorized_keys` on the box as a whole with a file holding only the new key and read it back with `diff`; (2) find a snapshot; (3) read it with the old password through a `backup-snapshot.env` that also sets `RESTIC_PASSWORD_FILE=/opt/bookclub/restic-password-old`; (4) a new repository with a new password, `restic init`, the password into the password manager; (5) steps 2–5 of "Restoring for real", whose `backup.sh` then writes into the new repository; (6) remove the copies. The old password, the repository and everything on the old VM (SMTP credentials, package token) count as known to the attacker; a box rollback is only for damage without a compromise, because it brings back the old password and the old `authorized_keys`.
- **A bad `UPDATE_WAIT_SECONDS` stopped the backups** (minor). The check moved from `load_config` to `update.sh`.
- **A failing backup was retried every 3 minutes** (minor). `update.sh` now waits `RETRY_AFTER` (1 hour) before it tries the same image again (`BACKUP_DIR/update.failed`: the image ID and the time); in between it pings `/1` and says when the next try comes. A new image for the tag, or `rm update.failed`, tries at once. The optional `--no-check` for the update's backup was not added: with the wait, a Sunday update runs the 5 % check once, not every 3 minutes.
- **The network section forbade the DNS server it relied on** (minor). Every other RFC 1918 address stays closed, except the VLAN's DNS resolver and time server (UDP/TCP 53, UDP 123), as work plan §5 item 10 lists DNS and NTP; without that exception, public resolvers and `/etc/hosts`.
- **The heartbeat URL went into the journal** (minor). `heartbeat` logs `warning: the heartbeat ping <what> to <host> failed`, and hands curl the URL as `url = "…"` on stdin (`-K -`), so it is not on the process list either. This applies to `backup.sh` and `restore-test.sh` too.
- **Missing tests** (four findings): the one-off containers, the empty container list, the lock, the check after `compose up` and the `RepoTags` guard now have tests (above), each shown to catch the mutation the reviewers named.
