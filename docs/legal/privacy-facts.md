# Privacy facts

These are the facts a privacy policy (Datenschutzerklärung) for the hosted Bookclub service needs, taken from the code with file references. They are input for eRecht24 or a lawyer, not legal text and not legal advice. Every "to confirm" is a decision Rafael still has to make, a value that only exists once the service goes live, or a point for the legal source to confirm. "To sign" marks a data processing agreement that is not signed yet.

The facts describe the Rust server (`server/`) and the Vue app (`frontend/`) on branch `phase-2`. Until the cutover (#52), production still runs the Python app in `backend/`; these facts apply from the cutover on.

## 1. Controller, hosting and contact

- **Controller:** Rafael, as the operator. Name and postal address go into the imprint (§ 5 DDG). To confirm: the address service (work plan §5 step 9).
- **Hosting:** the server runs on Rafael's own hardware (a Proxmox VM behind his own Caddy reverse proxy, on a business line with a static IP). No hosting provider processes the data. To confirm: the location (Germany) for the privacy text.
- **Contact:** one public contact and takedown address, `CONTACT_EMAIL` (default D3). The server publishes it in `GET /api/config` as `contact_email` (`server/src/auth/mod.rs`, `service_config`) and sends it in the User-Agent of its catalog requests (`server/src/outbound.rs:97-103`).
- **Legal texts:** the operator puts the imprint, privacy policy and terms (German and English) into `LEGAL_DIR`; the server serves them at `GET /api/legal/{doc}` and the app shows them at `/imprint`, `/privacy` and `/terms`, signed out too (`server/src/legal.rs`). Without them, the server refuses `SIGNUP_MODE=open` outside development.

**Pictures are public by URL.** The app shows a picture only where its owner's data is visible (the table above), but the file behind it, `GET /media/{public_id}/{variant}`, is served without a session: the random 26-character id in the URL (130 bits) is the secret (`server/src/media/serve.rs` (`get_media`), `server/src/media/shared/urls.rs` (`new_public_id`)). Whoever has the URL, for example from a copied link or the browser history of a shared device, can load the picture without an account. A picture is served with `Cache-Control: public, max-age=31536000, immutable`, so a browser that loaded it may keep its copy for up to a year, also after the user replaced it or an admin took it down; from then on the server answers 410 for a removed picture, and a new picture gets a new URL. To confirm with the lawyer: whether the privacy text needs to say this. A shorter cache lifetime for profile pictures is a possible follow-up.

## 4. Logs and IP addresses

- **The app log** (standard output of the container) has one line per request with the method, the path, the status, the latency and a random request id (`server/src/lib.rs`, `TraceLayer`). It has **no IP address, no User-Agent, no cookie and no user id**, with one exception: each suspension and each lifting of one writes a line with the numeric ids of the instance admin who did it and of the account (and, for a suspension, how many sessions it ended), at the default level `info` (`server/src/admin/users.rs` (`suspend`, `unsuspend`)). The hourly cleanup logs only how many rows of each kind it deleted (`server/src/auth/mod.rs` (`cleanup`)). Invite codes in paths are replaced by `{code}` (`loggable_path`). Outbound catalog requests are logged with their URL (`server/src/outbound.rs`), which contains the search text or the ISBN, but not who asked. Errors are logged without request bodies. Mails are never logged in production: the log transport, which writes every mail into the log, is refused outside development (`server/src/config.rs`, `EMAIL_TRANSPORT`). Retention: by size, not by time. Docker keeps at most 5 files of 10 MB per container (`deploy/hosted/compose.yaml`, `x-logging`), so the days the log covers depend on the traffic. To confirm with the lawyer: whether a log without IP addresses needs a time limit.
- **The reverse proxy** (Caddy, shared with Forgejo) logs every request to the service into a file of its own with the client IP address, the time, the method, the path, the status and the request headers, the User-Agent among them. Caddy writes cookies and credentials as `REDACTED`, and the log filter drops the Referer, replaces the query string with `?{redacted}` and invite codes in paths with `{redacted}`. logrotate on the proxy host rolls the file daily and keeps 5 old files, so no line is older than 7 days (`deploy/hosted/Caddyfile.example`, the comment above its `log` block; `deploy/hosted/README.md`, "Reverse proxy").
- **Rate limiting** uses the client IP address (an IPv4 address, or the /64 prefix of an IPv6 address, `server/src/ratelimit.rs:314-322`), taken from `X-Forwarded-For` only when the proxy is trusted (`server/src/client_ip.rs:41-65`), plus account ids, session ids (for the password checks of a signed-in session, `server/src/auth/account.rs` (`session_key`)) and SHA-256 hashes of login names that match no account (`server/src/ratelimit.rs:327-331`). The per-address mail limits (6 mails of each kind a day) are keyed by the recipient's email address itself, case-folded (`server/src/auth/mail.rs` (`target_key`, `deliver`)). Every address the server mails becomes such a key, including one somebody typed at sign-up or at an email change that belongs to a third person. These counters live in memory only, for at most 24 hours (the longest window, `server/src/ratelimit.rs:273-302`), and are gone after a restart. They are never written to disk or to the log.

## 6. The browser contacts no third party

- The app is one origin: the page, its scripts and styles, the API (`/api`) and every picture (`/media`) come from the service's own host. Covers from Open Library are fetched and stored by the server first (§5), so the browser never loads them from Open Library.
- No web fonts are loaded: the font stacks name fonts the device may have installed and fall back to system fonts (`frontend/src/styles/tokens.css:6-7`); the app ships no font files.
- No analytics, no error tracking, no CDN, no embedded media, no social plugins. The page's Content-Security-Policy limits it to its own origin (`server/src/spa.rs` (`SHELL_CSP`)).
- The only way out is a link the user clicks: "View on Open Library" on a book page, which opens in a new tab without a referrer (`frontend/src/pages/BookDetailPage.vue` (`book.viewOpenLibrary`)).
- The web app manifest and icons are local files (`frontend/public/`).
- The legal pages show the operator's HTML without pictures, frames, styles or scripts, and links to other sites open in a new tab without a referrer (`frontend/src/pages/LegalPage.vue` (`sanitizeLegalHtml`)), so a generator template cannot add a request to a third party.

## 8. Rights of the user

- **Access and portability (Art. 15, 20):** Settings → "Export my data" downloads a ZIP with `data.json` (every row that belongs to the user, from every table that references the account) and the pictures the user uploaded (`GET /api/auth/me/export`, `server/src/auth/export.rs:77`; contents in `docs/phase1/conventions.md` §5.7). Rows of clubs the user has left keep only what the user wrote. The reports section lists the reports the user filed or decided and, of the reports about the user's own content (their profile picture, pictures they uploaded, books and editions they added), only the removals, one entry per decision with its reason and date: open and dismissed reports, their number, their times and who filed them are withheld, because in a club of 2 to 5 they can name the reporter (Art. 15 (4) DSGVO, § 29 (1) BDSG; `takedown.md` §6). A profile picture held for a report is left out until it is decided. Five exports per hour.
- **Erasure (Art. 17):** Settings → "Delete account" with the password (`DELETE /api/auth/me`, `server/src/auth/deletion.rs` (`delete_user`)). Everything the user owns is deleted in one transaction: sessions, links, shelf, favourites, quotes, layout, search history, imports, memberships, reactions, ballots, events, profile pictures and posts (posts with replies by others become anonymous tombstones). An owner of a club with other members must hand it over or delete it first. Details: `docs/phase1/conventions.md` §5.6.
- **Rectification (Art. 16):** the user changes the email address, language, time zone and display settings in Settings. The username cannot be changed in the app; the operator changes it on request (to confirm how).
- **Suspended accounts (Q15, ADM2):** an instance admin can suspend an account. It then cannot sign in, its sessions are ended, and its content stays. It therefore loses the in-app export and deletion above (Art. 15, 17 and 20). Its owner writes to `CONTACT_EMAIL` instead, and the operator answers by hand: an export of the same content, or the deletion of the account, after checking that the request comes from the account's owner. `takedown.md` §7 holds the operator's steps (ADM2): for the export the account is unsuspended for a few minutes; the deletion still needs the owner's password, so the account is unsuspended for an agreed hour (to confirm). To confirm with the lawyer: how the owner proves the account is theirs (for example a mail from the account's verified address), and whether data needed as evidence for the suspension may be kept back from a deletion.
- **Accounts that stay empty** (no verified address, no data, no sign-in for 30 days) are deleted by the server itself (§7).
- **Objection, restriction, complaint:** by mail to `CONTACT_EMAIL`; the privacy text names the supervisory authority (to confirm).

## 9. Terms acceptance

Recommended option of Q13: a sentence with links above the sign-up button, with the version and the time stored.

- The operator's `manifest.json` names the current terms version; `GET /api/config` publishes it as `terms_version` (`server/src/legal.rs`).
- The sign-up page says, right above the button: "By creating an account, you accept the terms of use. The privacy policy explains what we store about you." Both are links (`frontend/src/pages/SignupPage.vue`). There is no checkbox.
- A sign-up must send that version whenever the terms are configured; the server stores it with the time (`users.terms_version`, `users.terms_accepted_at`; `server/src/auth/signup.rs`).
- Accounts without an acceptance of the current version (imported accounts, and everyone after a new version) see a prompt at the top of every page until they accept: "The terms of use of {service} are new or have changed. Please read them and accept them.", with an "Accept the terms" button (`frontend/src/components/TermsPrompt.vue`, `UserOut.needs_terms`). The button records the acceptance (`POST /api/auth/terms`, `server/src/auth/account.rs`). The prompt cannot be dismissed without accepting, and nothing else in the app is blocked meanwhile (to confirm with the lawyer).
- Both columns are part of the export (§8).

## 10. Inside the service: who sees whose data

- **Strangers see nothing** of a user in the app. The one exception: a picture whose URL they have, which loads without signing in (§2). People who share a club (the audience) see the username, the profile picture, the shelf, ratings and takes, diary entries, quotes, favourites, stats and the physical shelf, except items the user marked "only me" (`docs/phase1/conventions.md` §6.1).
- **Club members** see the club's posts, picks, votes, members and activity.
- **Instance admins** see the admin queue: reports (with the reporter's username, and for a profile picture whose it is), edit, merge and cover requests (with the requester's username), the sign-up invites, and the suspended accounts (username, picture, admin flag, sign-up and suspension time). No admin screen shows email addresses: the app sends the decision mails of Q12 A itself (ADM2), so an admin never needs a reporter's or uploader's address.
- **Email addresses** are never shown to other users. Sign-up and the email change never reveal whether an address is in use (`docs/phase1/conventions.md` §5.5).
